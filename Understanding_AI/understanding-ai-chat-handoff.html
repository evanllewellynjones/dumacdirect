Slide 5 — How a Neural Network Works ✅

Graphic: Node-and-edge network diagram — input layer (3) → hidden layers (4, 4) → output layer (2), fully connected. Annotate "Forward pass: data flows in →" above and "← Learning: weights adjusted (backpropagation)" below; label Input / Hidden layers / Output.

Bullets:
- Neurons are arranged in layers: an input layer, one or more hidden layers, and an output layer.
- Every connection carries a weight; each neuron adds up its weighted inputs.
- An activation function decides how strongly the neuron fires, letting the network capture non-linear patterns.
- Layer by layer, raw inputs are transformed into higher-level features.
- The output layer produces a prediction — a label, a number, or the next word.
- Training: the prediction is compared to the correct answer, then backpropagation nudges every weight to shrink the error — repeated over millions of examples.

Slide 6 — How an LLM Turns Words Into an Answer ✅

Graphic: Six-stage pipeline left→right with arrows; a worked example threaded through each box; a full-width "autoregressive loop" arrow pointing back to the start.

Stages (title · description · example):
1. Tokenize — Split text into vocabulary chunks (tokens). — "cats sleep" → [cats, sleep]
2. Assign IDs — Look up each token's integer ID. — [9245, 6134]
3. Embed — Turn each ID into a vector of decimals (stored as binary bits). — [0.12, -0.85, 0.03, ...]
4. Forward pass — GPU multiplies vectors through billions of learned weights + attention. — matrix math × N layers
5. Predict — Score every possible next token; softmax to probabilities. — sleep 0.62 / run 0.11 / eat 0.05
6. Decode — Sample one token, convert its ID back to text. — → "sleep"

Key note (on slide): Every number is stored as binary 1s and 0s. The GPU runs arithmetic over these numbers — it does not execute your words as a program.

Loop: Autoregressive — append the predicted token, repeat from step 4 to produce the next one, until a stop token.

Caveat: Illustrative values — real vocabularies hold ~100k+ tokens and each embedding vector is thousands of numbers long.

Slide 2a — Why Generative AI Happened When It Did: The Enablers ✏️ Draft

Suggested placement: right after Slide 2 (pairs with Slide 2b).
Graphic idea: Three inputs (Data · Compute · Algorithms) as arrows converging into one box: "Deep learning works — AlexNet, 2012."

Bullets:
- The ideas were old: the perceptron (late 1950s); backpropagation — the algorithm that trains a network — popularized in 1986 (Rumelhart, Hinton, Williams).
- Through two "AI winters," neural nets underperformed. The theory was mostly there; the fuel wasn't — nets too shallow, data too small, computers too slow to train anything deep.
- ~2012, three enablers hit critical mass at once:
- Data — internet-scale datasets. ImageNet (2009) = 14M labeled images; the web itself = a trillion-word text corpus.
- Compute — GPUs (built for graphics) are ideal for the parallel matrix math nets need; NVIDIA CUDA (2007) made them programmable for it.
- Algorithms — techniques that finally made deep networks trainable.
- Proof of concept: AlexNet (2012) — a deep net trained on GPUs crushed the ImageNet contest, roughly halving error overnight. It ended the AI winter and kicked off the deep-learning boom.
- Caveat: AlexNet is discriminative (it classifies images), not generative — this was the enabling tipping point, not the generative one.

Slide 2b — The Generative Tipping Point: Transformer + Scaling + Self-Supervision ✏️ Draft

Suggested placement: right after Slide 2a.
Graphic idea: Left→right flow — "Transformer (2017)" → "Self-supervised pretraining" → "Scaling laws: GPT-1→2→3 (2018–2020)" → "RLHF + ChatGPT (2022)"; caption: "turns more compute + data into reliably better."

Bullets:
- Three linked breakthroughs turned deep learning into generative AI:
- The Transformer ("Attention Is All You Need," 2017): self-attention lets the model look at all words at once; training is fully parallel (so it can actually use all those GPUs); captures long-range context. Replaced slow, sequential RNNs/LSTMs. The key architectural unlock.
- Self-supervised pretraining: train the model to predict the next (or a masked) word — any text is its own label, so the whole internet becomes training data. Removes the human-labeling bottleneck.
- Scaling laws (~2020): more data + more compute → predictably better, with new abilities emerging at scale. GPT-1 → GPT-2 → GPT-3 (2020, 175B params) showed "just make it bigger" keeps working.
- The combination is the point: an architecture that soaks up compute + a method that soaks up data + a scaling law that makes spending on both pay off = decades of incremental research turning into an explosion.
- Public tipping point: ChatGPT (Nov 2022) — RLHF (reinforcement learning from human feedback) + instruction-tuning turned a raw next-word predictor into an instruction-following conversationalist; generative AI went from research capability to mass product.
- Three senses of "tipping point": technical = Transformer + self-supervision + scaling (2017–2020); underlying enabler = the 2012 GPU-compute + internet-data convergence; cultural/market = ChatGPT (late 2022).
- Through-line: the missing ingredient was never the idea of neural nets — it was enough compute and data, plus an architecture that turns "more of both" into "reliably better" without hand-labeling.

Sources / caveats: Established ML history (within knowledge; no live web sources needed). Key references if citing: Rumelhart–Hinton–Williams 1986 (backprop); Krizhevsky et al. 2012 (AlexNet); Vaswani et al. 2017 (Transformer); Kaplan et al. 2020 (scaling laws); Brown et al. 2020 (GPT-3); Ouyang et al. 2022 (InstructGPT/RLHF).

Slide 7 — Why a Model's Knowledge Lags Its Release Date ✏️ Draft

Graphic idea: Two-point gap timeline — "Pretraining data cutoff (~May 2025)" ──gap──▶ "Release (May 2026)", with the intervening steps labeled along the gap.

Bullets:
- Training cutoff ≠ release date. Pretraining freezes a snapshot of data; the model ships months later.
- After the cutoff: post-training (fine-tuning, RLHF), evaluations, red-teaming, safety review, staged rollout — typically several months.
- Point releases stretch the gap: "4.x" versions are refined mostly via post-training on a base model whose pretraining cutoff is older and shared across the family — so a May-2026 model can still "know" only to ~May 2025.
- The stated cutoff is conservative: it's the date past which the model is unreliable, often set earlier than the actual last data ingested.

Example: Claude Opus 4.8 — reliable knowledge cutoff end of May 2025, released May 28, 2026 (~12-month gap).

Sources / caveats: Anthropic "Introducing Claude Opus 4.8"; Claude Platform Docs (models overview); Claude Help Center (training-data recency). Exact internal pretraining cutoff vs. the conservative "reliable" cutoff isn't publicly detailed.

Slide 8 — What Are LLMs Written In? ✏️ Draft

Graphic idea: Two-layer stack — top band "What people write: Python" over bottom band "What the GPU runs: C++ / CUDA"; a small side note lists the framework/serving tools.

Bullets:
- The code humans write to define and train LLMs is overwhelmingly Python.
- Python is glue: it drives frameworks — PyTorch (dominant), JAX (Google/DeepMind), formerly TensorFlow.
- Those frameworks are themselves C++ with CUDA (NVIDIA's GPU language) — where the heavy matrix math actually runs.
- Custom GPU kernels are increasingly written in Triton (a Python-like language) instead of raw CUDA.
- Inference/serving adds more C++ and, increasingly, Rust — e.g. llama.cpp (C/C++), Hugging Face tokenizers & serving (Rust), vLLM (Python + CUDA).

Short version: Python for what people write, C++/CUDA for what the GPU runs.

Slide 9 — The Hardware Behind LLMs: PC vs Data Center ✏️ Draft

Graphic idea: Two-column comparison — left "Personal PC (local inference)", right "Data center (inference at scale)", each listing components with a one-line role; a bottom band with the shared bottleneck.

Personal PC (local inference):
- GPU — does the parallel matrix math; consumer NVIDIA RTX (RTX 5090 = 32 GB, top consumer) or Apple Silicon.
- VRAM — the hard limit on model size; ~0.6 GB per billion params at 4-bit (7B ≈ 5 GB, 70B ≈ 40 GB). Plus the KV cache (working memory for the current context) — e.g. an 8B model at Q4 ≈ 4.7 GB weights + ~4 GB for a 32K-token context = ~8.7 GB, which overflows an 8 GB card (the common out-of-memory cause).
- System RAM — load/staging & CPU fallback; 16–32 GB; does not decide what fits on the GPU.
- CPU — orchestration, tokenization; runs layers offloaded when VRAM runs out (slow).
- NVMe SSD — stores multi-GB weights; speeds model loading.
- PSU + cooling — high-end GPUs draw ~575 W; need headroom.
- Quantization — compresses weights (Q4_K_M ≈ 90–95% quality at ~25–30% VRAM) to fit bigger models.

Data center (inference at scale):
- Accelerators — NVIDIA Blackwell B200 (192 GB HBM3e, 8 TB/s) / B300 Ultra (288 GB HBM3e, H1 2026); ~30× LLM inference vs H100. Alt: AMD MI300X, Google TPU, AWS Inferentia/Trainium, Groq, Cerebras.
- HBM — on-package high-bandwidth memory; inference is bandwidth-bound (stream weights per token); capacity sets model-per-chip.
- NVLink — ultra-fast GPU↔GPU (1.8 TB/s) so many GPUs act as one (GB200 NVL72 = 72 GPUs pooled).
- InfiniBand / Ethernet — 400–800 Gb/s scale-out across nodes and racks.
- Host CPU — NVIDIA Grace CPU, fused with GPU as a "superchip" (Grace + Blackwell) to feed/orchestrate.
- Storage — parallel NVMe file systems for weights and datasets.
- Power & liquid cooling — racks at tens of kW; liquid-cooled (NVL72) — "AI factories".

Through-line (bottom band): A PC pools nothing (one GPU, VRAM-limited, quantized, one user); a data center pools many accelerators via NVLink + InfiniBand to hold full-size models in HBM and serve many users with batching. Both are gated by memory bandwidth — moving weights, not just multiplying them.

Sources / caveats: NVIDIA Blackwell specs (slyd/NVIDIA); local-LLM guides (promptquorum, quantizelab) as of July 2026. Consumer GPU prices volatile (GDDR7 shortage).

Slide 10 — Who Makes the Memory? HBM as the AI Bottleneck ✏️ Draft

Graphic idea: A single horizontal stacked share bar for HBM (SK Hynix ~62% | Micron | Samsung) + a small row of scarcity stat callouts below. Optional inset: a mini stack diagram (8–12 DRAM dies + TSVs) to show why it's hard.

Bullets:
- Ordinary DRAM/GDDR is a commodity; HBM is not — only three companies on Earth make it.
- Market: SK Hynix ~62% (Nvidia's primary supplier) · Micron #2 (overtook Samsung in 2026) · Samsung #3 (pushing HBM4 to regain share).
- Why it's hard: 8–12+ DRAM dies stacked vertically and wired with thousands of through-silicon vias (TSVs); high yield needed; eats far more wafer capacity per bit than standard DRAM and competes for the same fab lines.
- Second bottleneck downstream: attaching HBM to the GPU needs advanced packaging (TSMC CoWoS), itself capacity-limited.
- The inversion: memory used to be the cheap, swappable part; now it gates the whole AI buildout. SK Hynix / Micron / Samsung are as strategic as Nvidia and TSMC.

Scarcity signals (2026) — stat callouts:
- 36–52 wks — data-center GPU lead times (HBM-driven); ~3.6M-unit backlog (Apr 2026)
- +30% — HBM price rise in Q4 2025 alone
- ~$450–470B — hyperscaler AI capex that booked most HBM through 2027 (effectively sold out ahead)
- −30–40% — Nvidia's cut to RTX 50-series consumer GPU output to redirect memory capacity

Sources / caveats: Astute Group, Value Add VC, EnkiAI, SK Hynix 2026 outlook — as of July 2026. Shares/prices move fast; exact Micron vs Samsung split approximate; HBM4 ramping.

Slide 11 — Why HBM Supply Can't Just Scale Up ✏️ Draft

Graphic idea: Two columns — left "Why no fourth maker (barriers to entry)", right "Why the three can't make more (scaling limits)". Optional inset: a series-bottleneck strip (DRAM wafers → HBM stacking → TSMC CoWoS packaging) to show two chokepoints in a row.

Why no fourth maker (barriers to entry):
- Must already run a leading-edge DRAM fab — only SK Hynix, Samsung, Micron do. DRAM is off Moore's law (6F² cell since 2004; 50:1 capacitor aspect ratios), so catching up takes years and tens of $B.
- Punishing stacking process: thin 12–16 dies to 30–50 µm, wire with thousands of TSVs, stack to <~775 µm with near-perfect alignment, bond, and test each die before and after (one bad die kills the stack). Yield loss compounds per layer.
- HBM4 raises the wall: the base/logic die can no longer be made on a DRAM process — it needs an advanced logic foundry (TSMC 3nm-class), tying memory makers to TSMC and favoring the largest incumbents.
- China's CXMT is trying but sits generations behind and is limited by export controls on tools.

Why the three can't make more (scaling limits):
- Wafer trade-off (core): HBM uses far more wafer area per usable bit; every wafer moved to HBM is pulled from commodity DDR5/GDDR — the direct cause of the broader 2026 DRAM shortage and price spikes.
- Capacity takes years: new cleanrooms are 2–3-year builds; specialized gear (TSV etch, thin-wafer bonders, stack testers) has long lead times.
- Second chokepoint in series: finished HBM must be co-packaged onto the GPU via TSMC CoWoS, which is also capacity-limited.

Takeaway: A structural triopoly, not a temporary shortage a new supplier will relieve.

Sources / caveats: Vik's Newsletter (HBM manufacturing), Tom's Hardware & DigiTimes (HBM4 base die / TSMC), The Economy (wafer bottleneck), SemiAnalysis (CXMT) — as of July 2026.

Slide 12 — Weights: Written in Training, Read-Only at Inference ✏️ Draft

Suggested placement: conceptually belongs right after Slide 6 (LLM pipeline); final order decided at build.
Graphic idea: Two panels. Left "Training" with a loop (forward → compare to correct answer → backpropagation → update weights) labeled weights change. Right "Inference" with a one-way flow (input → read weights → output) labeled weights fixed. Small legend distinguishing weights vs activations/KV cache.

Bullets:
- Weights = the billions of learned numbers. Set during training, frozen afterward.
- Training: weights are read and written — backpropagation computes the error and updates every weight. This is where they change.
- Inference: weights are read-only — loaded and multiplied against your input to predict the next token; the values never change.
- What does change at inference: activations and the KV cache — transient numbers computed fresh for your prompt, then discarded.
- "Streaming" or "moving" weights at inference means reading them, not editing them — which is why it's a memory-bandwidth (read) problem, not a writing one. A 70B model = ~40 GB of weights read for every token.
- Analogy: training writes the cookbook; inference reads the recipe. Cooking 1,000 meals reads the recipe 1,000 times but never rewrites it.

Slide 13 — Building Reliably with an Unreliable Model: LLM Steers, Deterministic Code Executes ✏️ Draft

Graphic idea: Flow — "Natural-language request" → [LLM: understand intent + choose action] → "structured call (function / JSON / SQL)" → [Deterministic system executes] → "result" → [LLM phrases the answer].

Bullets:
- Principle: let the LLM do only what it's uniquely good at (understanding messy natural language); hand everything that must be exact to deterministic code.
- Never make the LLM be the calculator, database, or rules engine — make it decide which to call and with what inputs.
- Mechanisms: tool use / function calling; structured/constrained output (valid JSON, schema-checked); retrieval (RAG) to ground facts; neurosymbolic (neural language + symbolic logic/solver).
- The LLM becomes a translator + orchestrator: NL in → structured intent → deterministic execution → NL out.
- Removes whole error classes — arithmetic, lookup, sorting, formatting — anything expressible as code.

Slide 14 — The Catch: You Move the Error, You Don't Delete It ✏️ Draft

Graphic idea: Text-to-SQL example — "How many active customers in Q2?" → LLM writes SQL (probabilistic) → DB runs it (deterministic) → precise but possibly wrong number. Callout: deterministic execution ≠ correct decision.

Bullets:
- The boundary itself is probabilistic: the LLM still picks which tool and what arguments — that NL→structured-call step is the 90% part.
- The deterministic backend faithfully executes the wrong call if the LLM chose wrong. The error is relocated, not removed.
- Example: text-to-SQL — the database is deterministic, but wrong SQL from your question yields a confident, precise, wrong answer.
- What it still buys: shrinks the fuzzy surface to "understand intent + choose action"; makes errors catchable (schema checks, validators, business-rule vetoes, a second model to verify); enables safe failure (confidence thresholds, abstention, human-in-the-loop).
- Honest limit: the NL→action step can't be made provably 100% reliable. Shrink the LLM's role, wrap the rest in checkable code, design for graceful failure. A well-built AI product is mostly ordinary deterministic software the model steers.

Slide 15 — Vague Prompts & the Clarification Gap ✏️ Draft

Graphic idea: Two contrasting bars — "Recognizes ambiguity when asked: 60–80%" vs "Actually asks a clarifying question: 0–5%".

Bullets:
- Much of the error is the model guessing among valid interpretations instead of asking.
- 2026 finding ("Knowing but Not Showing"): models judge ambiguity correctly 60–80% when asked, but ask clarifying questions only 0–5% of the time in normal use (Claude highest, ~5%). Capability present, behavior absent.
- Counterintuitive: giving context (RAG) suppresses clarification further — "I have documents" reads as "answerable."
- Root cause: RLHF rewarded confident, complete answers over "it depends," so models learned guessing looks more helpful. An alignment/behavior gap, not a knowledge gap — so it's trainable.

Slide 16 — Closing the Gap: Making LLMs Ask Well ✏️ Draft

Graphic idea: CLAM-style pipeline — classify ambiguity → ask if needed → incorporate answer → respond; side note "reward asking only when it improves the final answer."

Bullets:
- Train to ask — and only when it pays off: SFT on clarification dialogues (CAMBIGNQ, 5,653 queries); RL/self-play (STaR-GATE, ~72% human preference); "double-turn preference" (reward clarifications that lead to a correct next answer). Over-asking is penalized.
- Detect when to ask: use the model's own uncertainty (APA). Caveat: "Uncertainty Quantification Fails under Ambiguity" (Nov 2025) — confidence is least reliable exactly when the query is ambiguous.
- Reason first: chain-of-thought, self-ask, Tree-of-Clarifications; reasoning models (2025–26) surface the fork before committing.
- System-level (most reliable today): wrapper pipelines (CLAM: classify→ask→incorporate); a small model to disambiguate the prompt before the big LLM; product patterns (slot-filling, "did you mean…", confirmation before high-stakes actions).
- Benchmarks reframe it as a tradeoff: "One More Turn, Less Regret" (Jul 2026) scores clarification policies by regret — cost of asking unnecessarily vs. guessing wrong.
- It's a tradeoff, not a bug: ask too much = annoying; too little = wrong. Trajectory = better-calibrated asking, not perfect intent-reading. Complement: have the system state its assumption ("interpreting 'active' as logged-in ≤30 days…") so a wrong guess is visible and cheap to correct.

Sources / caveats: Knowing but Not Showing (2026); "Teaching AI to Clarify" synthesis (May 2025); One More Turn, Less Regret (Jul 2026); UQ Fails under Ambiguity (Nov 2025); Modeling Future Conversation Turns (OpenReview). As of July 2026; default asking rates still low.

Slide 17 — Customizing an LLM: The Ladder ✏️ Draft

Graphic idea: A 4-rung ascending-steps graphic — Prompting → RAG → Tool use → Fine-tuning ("cheapest/fastest" at bottom → "heaviest" at top). Side callout box: RAG vs Fine-tuning.

Bullets:
- Customization is a ladder — try the cheapest rung first:
1. Prompting / system prompt — free, instant; often enough.
2. RAG (retrieval) — give the model your documents at query time (open-book).
3. Tool use — connect it to your systems.
4. Fine-tuning — actually change the model's weights; the heaviest lever, reach for it last.
- Key distinction:
- RAG = new knowledge it should know (facts, policies, docs — especially things that change). Open-book.
- Fine-tuning = new behavior/skill — how it should act: house format, tone, domain reasoning, following a schema, a specialized task. Changes its instincts.
- Rule of thumb: RAG for what it should know, fine-tuning for how it should behave.
- Common mistake: fine-tuning to "add facts" — the model blurs them and they go stale; use RAG for knowledge.
- If prompting + RAG gets you there, don't fine-tune — cheaper and easier to update.

Slide 18 — What Fine-Tuning Is, and the Methods ✏️ Draft

Graphic idea: A frozen base model with small highlighted "adapter" blocks (LoRA); a legend listing the methods ordered by cost.

Bullets:
- What it is: continue training a pretrained model on curated input→output example pairs so its weights shift toward your desired behavior. You're not teaching it English — you're teaching your way of doing a specific job by showing hundreds–thousands of ideal examples.
- Methods, cheapest → heaviest:
- LoRA (default) — freeze the big model, train tiny low-rank adapter matrices (~0.1–1% of params). Cheap, fast, swappable.
- QLoRA — LoRA on a 4-bit quantized base → fine-tune a large model on a single GPU. Democratized fine-tuning.
- Full fine-tuning — update all weights. Powerful but expensive; risks catastrophic forgetting. Rare for most teams.
- Preference / RL tuning — DPO (learn from preferred-vs-rejected answer pairs to shape style/judgment); GRPO / reinforcement fine-tuning (reward-based; great when answers are checkable, e.g. reasoning). Used after basic supervised fine-tuning to refine.
- Managed APIs — OpenAI/Anthropic/Google run training from an uploaded example file (easiest); open-weights + LoRA for control/privacy.
- Supervised fine-tuning (SFT) on instruction→response pairs is the workhorse base step.

Slide 19 — Fine-Tuning Step by Step: A Worked Example ✏️ Draft

Graphic idea: An 8-step numbered flow with an example banner: "Law firm — contract → house-style risk memo."
Goal: an LLM that reads a contract and drafts a risk-review memo in the firm's house format, flagging problematic clauses.

  1. Define the task + decide RAG vs FT. Narrow to one job: contract → risk memo. Firm precedents/playbook = RAG (updating knowledge); house style + memo structure + risk-flagging behavior = fine-tuning (a skill).
  2. Collect & curate data — 80% of the work. ~500–2,000 pairs of (contract excerpt → ideal senior-associate memo) from past matters; clean, de-identify, ensure genuinely exemplary. Quality > quantity.
  3. Format into instruction pairs. {system: "You are the firm's contract reviewer…", user: <contract text>, assistant: <ideal memo>}. Hold back a test set the model never sees.
  4. Pick base model + method. Open model (Llama/Qwen/Mistral-class) for control/privacy, or a provider fine-tuning API. Use QLoRA to train adapters cheaply.
  5. Train. A few epochs; with QLoRA, hours on one/few GPUs, often tens–low-hundreds of dollars for a small model. Watch for overfitting.
  6. Evaluate against baselines. On held-out contracts: format match, catches risky clauses, no invented terms. Rubric + human review (+ optional LLM-judge). Compare vs base model and RAG-only — if it doesn't beat those, don't ship.
  7. Iterate. Patch data gaps, add hard/edge cases, retrain. Optionally DPO on better-vs-worse memos to sharpen style/judgment.
  8. Deploy with the full stack. Fine-tuned model (house style) + RAG (precedents) + tool use (clause database) + human-in-the-loop (legal — never fully autonomous). Monitor; feed lawyers' corrections into the next round (a flywheel).

Slide 20 — Fine-Tuning: Pitfalls & When (Not) To ✏️ Draft

Graphic idea: Two-column do/don't, or a set of warning callouts.

Pitfalls:
- Don't fine-tune for changing facts — that's RAG's job; fine-tuned facts go stale and blur.
- Catastrophic forgetting — over-training erodes general ability; LoRA + modest, high-quality data mitigates it.
- Garbage in, confident garbage out — the model faithfully learns whatever the examples teach, flaws included.
- Try the cheaper rungs first — many "we need to fine-tune" problems are solved by a better prompt + RAG.
- Cost reality: LoRA/QLoRA made it accessible — a 7–13B fine-tune can be tens–hundreds of dollars, not millions.

When to actually fine-tune: consistent format/tone/style; a narrow, repeated task; latency/cost (a small fine-tuned model replacing a big general one); or behavior that prompting can't reliably enforce.

Sources / caveats: Future AGI (LoRA/QLoRA/DPO/GRPO, 2026); BigData Boutique (RAG vs fine-tuning, 2026); Umesh Malik (RAG vs fine-tuning, 2026). Methods stable as of July 2026; tooling names churn.

— On-Prem & Open Models cluster (Slides 21–23) —

Slide 21 — A Model Is Just a File: Download vs. Run ✏️ Draft

Graphic idea: Two panels — "On disk (download)" vs "In GPU memory (run)"; a size-math strip; Kimi K3 numbers as the extreme case.

Bullets:
- A trained model = its weights = a file of numbers. Downloading a model = downloading that file. "Open weights" = the company published the file (e.g., on Hugging Face).
- Size math: file ≈ params × bytes/param. FP16 = 2 bytes (7B ≈ 14 GB, 70B ≈ 140 GB); 4-bit ≈ 0.5 byte (7B ≈ 4 GB, 70B ≈ 35–40 GB).
- Small models (1–8B) are small files — download and run on a laptop. No contradiction.
- Kimi K3 (Jul 2026) shows the other extreme: 2.8T params, MXFP4 4-bit → ~1.4 TB download (vs ~5.6 TB at FP16); MoE routes only ~50B active/token (16 of 896 experts).
- Download ≠ run: the 1.4 TB file is public and downloadable, but loading it needs ~1.4 TB of GPU memory — in practice an 8-node cluster of 8×80 GB (~5.12 TB). "Open" = access to the file, not that it fits your machine.
- MoE cuts running cost (computes like a ~50B model) but not storage (must hold all 2.8T in memory).

Slide 22 — Running a Model On-Premises: Right-Size, Quantize, Serve ✏️ Draft

Graphic idea: Hardware-tier ladder (7B → 70B → frontier) with GPU counts + $; a "serving" box (vLLM / NIM) feeding an internal API.

Bullets:
- "Too big" usually points at the wrong thing: disk footprint is trivial; the real constraint is GPU memory to hold + run. Inference is far lighter than training — no training supercomputer needed.
- Two levers: right-size the model + quantize.
- Tiers (2026): 7–8B → one 24 GB GPU (RTX 4090), ~$15K server; 13–34B → one 48–80 GB card; 70B → 2–4× H100 or one H200 (or ~35–40 GB at 4-bit on a 48 GB card); frontier (Kimi K3 / 405B-class) → multi-node cluster (8–16 nodes of 8× H100/B200).
- Serving: vLLM (free; PagedAttention; ~4× throughput; OpenAI-compatible API) or NVIDIA NIM (~$4,500/GPU/yr; support + SLA). Apps point at an internal endpoint.
- Why on-prem: data sovereignty/compliance (GDPR, healthcare, finance, defense); cost at scale; control (weights + logs stay inside); air-gap; free fine-tuning.

Slide 23 — On-Prem Economics & Why Many Still Don't ✏️ Draft

Graphic idea: A break-even curve (cost vs. utilization) showing on-prem wins only past a high sustained-load threshold; plus a "does on-prem fit us?" checklist.

Cost reality (corrected):
- ~$712K–948K over 3 years ≈ one 8-GPU (8×H100) server — runs up to a ~70B model comfortably. Not enough for frontier: Kimi K3 (2.8T) needs 8–16 nodes = many millions.
- The "~3.7-month payback vs cloud" holds only at high sustained utilization (billions of tokens/month, GPUs busy). At modest or spiky usage the GPUs sit idle and on-prem is more expensive than pay-per-token cloud. On-prem is cheaper only at scale.

Concrete reasons NOT to run on-prem (beyond cost):
- Capability gap: the best models (Claude/GPT/Gemini top tier) are closed, cloud-only; open weights typically trail the closed frontier ~6–18 months. On-prem = sovereignty over cutting-edge capability.
- Operational/talent burden: GPU ops, serving tuning, quantization, model upgrades, monitoring, security patching, driver/CUDA, hardware failures — a whole MLOps function most companies lack. Cloud APIs need ~none of it.
- Obsolescence + procurement: GPUs depreciate fast, and a new efficient model may need more VRAM than you bought. Plus GPU lead times are 36–52 weeks in 2026 — you can't buy a cluster next month; cloud holds priority allocation.
- No elasticity: on-prem is a fixed ceiling — can't absorb a 10× spike; you size for peak (wasteful) or get throttled. Cloud scales to zero and to peak.
- Facilities: a cluster draws tens of kW; needs power/cooling (often liquid), rack space, physical security — many offices can't host it; colo adds cost/complexity.
- Time-to-value & breadth: cloud API integrates in an afternoon and offers many models (text/image/video/speech) via one endpoint; on-prem is weeks–months to first token, each model a separate deployment.
- Security is double-edged: keeps data in, but you now own securing the whole stack — a big cloud provider may have a stronger posture than a small self-run cluster.

Who on-prem actually fits: regulated + privacy-critical + high, predictable sustained volume + OK with slightly-behind-frontier open models. A real and growing segment — not a universal direction.

Sources / caveats: iternal.ai on-prem guide (2026); GPU/HBM lead times 36–52 wks (Slides 10–11 sources). As of July 2026; hardware prices/lead times volatile.

Slide 24 — The Deployment Spectrum (It's Not On-Prem vs Public API) ✏️ Draft

Graphic idea: A left→right spectrum with an axis: "data leaves ← → data stays in your boundary." Four stops, each with a one-line note on capability/effort tradeoff.

Bullets:
- The choice is not binary — there's a spectrum, and enterprises live in the middle:
1. Public API — data goes to the vendor endpoint (contractual zero-retention).
2. In-your-own-cloud — Claude via Amazon Bedrock / Google Vertex, GPT via Azure OpenAI: the model runs inside the customer's own cloud tenancy/region, no training on your data.
3. Dedicated / managed — provisioned capacity or vendor-run secure infra (e.g. "Claude Managed Agent").
4. On-prem open-weights — self-host. The far end.
- Key point: by tier 2–3 a company already has data control that satisfies regulators and model-risk teams — data stays in its boundary, contractually untrained-on — without owning GPUs or accepting a weaker open model.
- That combination is exactly why OpenAI/Anthropic can win the most regulated, security-conscious clients — it removes the main reason to go on-prem.

Slide 25 — Why Even Fortune 500 Banks Buy Frontier Instead of Self-Hosting Open Source ✏️ Draft

Graphic idea: A "money + talent removes these barriers ✔ / but not these ✘" two-column, with the bank evidence as a footer strip.

Real-world evidence (2026):
- JPMorgan's internal "LLM Suite" is a bank-built portal tapping OpenAI + Anthropic models, refreshed ~every 8 weeks.
- Claude in production at JPMorgan, Goldman Sachs, Citi, AIG, Visa; Jamie Dimon described using Claude Code to build an analysis dashboard in ~20 min.
- The richest, best-staffed institutions chose to rent frontier, not self-host open — for flagship work.

Why money + talent don't tip them to on-prem open source:
- Capability gap is unbuyable: the frontier is closed; open weights trail ~6–18 months. Spending can't turn an open model into frontier quality, and finance is high-stakes.
- Private deployments already solve data control: in-cloud/VPC + no-retention/no-training contracts + compliance certs ≈ sovereignty, without GPUs or open weights.
- Inference infra isn't the bank's edge: self-hosting is undifferentiated heavy lifting; the real bottleneck is integration/adoption — JPMorgan's Derek Waldron's "value gap." Scarce engineers belong on the last mile.
- Pace: frontier moves every ~8 weeks; buy-as-a-service = always-latest with no re-capitalization; self-host freezes you at your deployed model.
- Risk transfer & safety: banks want SLAs, IP indemnity, safety/jailbreak tuning, attestations, and model docs for model-risk governance (SR 11-7). Self-hosted open = the bank owns all model risk with no backstop.
- Reliability/support for mission-critical: vendor-managed infra, uptime, solutions teams, early access — key for "organizational absorption" at scale.

Honest nuance — they do BOTH: banks self-host open models selectively (internal doc search, code on proprietary repos, PII-heavy batch) where "good enough + cheap + fully internal" wins, and route the hardest work to frontier providers. JPMorgan built the portal/integration (their differentiation) and rented the models (not their differentiation).

Takeaway: money/talent remove the cost + ops objections to on-prem, but not the three that decide it — (1) can't buy frontier quality in open weights, (2) private deployments already give data control, (3) inference infra isn't where a bank creates value.

Slide 26 — How AI Is Priced: Subscription vs Metered API ✏️ Draft

Graphic idea: Two columns — "Consumer subscription (flat)" vs "API / enterprise (metered per token)"; buffet vs à-la-carte analogy.

Bullets:
- Two pricing models collide:
- Consumer subscription (Claude Pro $20, Max $100 / $200): flat monthly fee for access + a usage allowance, throttled by message rate limits — not billed per token. "Paying for compute capacity, not per token."
- Max 5x ($100) ≈ 225 messages / rolling 5-hour window; Max 20x ($200) ≈ 900 / 5-hour. Plus weekly caps.
- API / usage-based (developers, enterprises building apps): billed per token — input and output priced separately, per model tier (Opus > Sonnet > Haiku). Itemized per request.
- Why the flat plan shows no per-token cost:
- Tokens aren't the billing unit — the month is; there's no line item to show.
- Predictability + no bill shock; removes the "meter running" friction; encourages use.
- Smooths wildly variable per-message cost (500 tokens vs 200,000). Anthropic bets on average usage; light users subsidize heavy ones.
- Your real cost/answer on the subscription ≈ $0 marginal until you hit the limit; effective cost = $100 ÷ answers used → the more you use it, the cheaper each answer. The per-token figure is undefined by design.
- Estimate trick: count tokens × public API per-token rate = "what it would cost on the API" (not what you actually pay).

Slide 28 — What Drives Your AI Usage: The Cost Levers ✏️ Draft

Graphic idea: A ranked ladder/bars, cheapest → most expensive, of the consumption drivers.

Bullets:
- On a flat plan there's no monthly token pool and no exact % meter: limits are rolling 5-hour session caps + weekly caps, measured opaquely (a blend of prompt length, file size, conversation length, model, feature, capacity). Your signal = the "approaching your limit" warning.
- What burns allowance, cheapest → most expensive:
1. Model choice (biggest lever): Opus ≫ Sonnet ≫ Haiku.
2. Output length — generating lots of text/code.
3. Context / conversation length — every turn re-sends the whole history; long chats get progressively costlier even when new questions are short.
4. File uploads / attachments — big sheets/PDFs/images add input context on each reference.
5. Extended thinking / reasoning — extra tokens before the answer.
6. Tool use / agentic loops (the sleeper): Claude Code, Claude for Excel, Cowork make many hidden model calls per action (read→reason→act→observe→repeat) — 10–50× a single chat turn.
- Worst combos stack these: Opus + big file + long session + many iterations.
- Defenses: use Sonnet for routine work; start fresh chats to shed context; avoid dumping huge files; watch the limit warnings.

Slide 29 — Practical: Website Build & Claude for Excel vs Desktop ✏️ Draft

Graphic idea: Two worked mini-cases, each with a "how much does it cost me?" verdict.

Bullets:
- Reframe: limits are per 5-hour session + weekly, not a monthly pool — so the real question is "will this blow my current window," not "% of my month."
- Case 1 — build a 5-page HTML site: a one-shot build ≈ tens of thousands of output tokens = a small slice of one 5-hour session (low single digits), not 50% of your month. What inflates it: Opus, ~20 rounds of revisions (each re-sends the growing codebase as context), large reference files/images. Tip: build in Sonnet; start a fresh chat per page.
- Case 2 — Claude for Excel vs desktop chat: Excel is meaningfully more token-intensive — the agentic add-in reads the whole workbook, tracks cross-tab dependencies, and runs multiple tool calls to make + verify changes (the most expensive mode). Some users "maxed out Pro in 5 minutes" after a few Excel tasks.
- One pivot table on a small tidy sheet = modest (not 20% of your month). A pivot on a large multi-tab workbook, iterated, in Opus = burns fast (whole workbook is context every loop).
- Guidance: if you know how and the sheet is simple, DIY is cheaper (your instinct is right); if using the agent, pick Sonnet not Opus; reserve the agent for cross-tab reasoning that saves real time, not one-liners.
- Bottom line: a single website or single pivot table won't blow your month; long Opus sessions, giant files, and agentic tools on big inputs are what do.
